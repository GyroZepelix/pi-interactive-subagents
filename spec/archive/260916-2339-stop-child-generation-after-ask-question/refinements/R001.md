# Refinement R001: Replace early termination with a blocking question rendezvous

Work item: `260916-2339-stop-child-generation-after-ask-question`
Revision: `R001`
Status: Ready for spec
Created: 2026-09-16
Updated: 2026-09-16

## Trigger and evidence

The initial fix added `terminate: true` to `ask_question`. That prevents the immediate post-tool inference only when every finalized result in the same tool batch terminates. The user requested a better implementation that truly waits for the parent and chose a KISS design after comparing a new answer-sidecar protocol, a bare next-input capture, and correlated capture over the existing tmux path.

Pi 0.85.1 source confirms:

- A tool `execute()` promise may remain pending while the agent run is active.
- Interactive input submitted during an active run reaches extension `input` handlers before Pi queues it as steering.
- An `input` handler returning `{ action: "handled" }` prevents that message from entering the steering queue.
- Extension commands are dispatched before `input`, so an opaque non-command envelope is required for arbitrary parent replies.

## Objective

Keep `ask_question` pending until one matching orchestrator reply arrives, consume that reply without queueing a second child turn, return it as the tool result, and then let the same agent run continue normally.

## Affected contract

- Replace the canonical `terminate: true` and parked-new-turn design with a blocking tool promise.
- Extend the existing `.ask` payload with a unique question ID and write it atomically.
- Preserve the existing tmux transport for the answer, but encode the answer and question ID in a private JSON envelope that cannot be mistaken for a slash command.
- Intercept the matching envelope in the protected child `input` handler, acknowledge it, return `handled`, and resolve the pending tool.
- Preserve exact delivered/unconfirmed reporting with an ID-only acknowledgment marker.
- Keep generic running messages, finished-session resume, profile isolation, capability grants, and ordinary tmux behavior unchanged.

## Affected completed work

The current uncommitted `terminate: true` source change, its focused assertion, and documentation describing early tool-batch termination are superseded by this revision. The original root-cause finding remains valid: an ordinary immediately completed tool result causes a post-tool inference. Existing `.ask` notification, watcher, safe tmux submission, interruption recovery, and no-replay decisions remain reusable.

The earlier `verification.md` describes the superseded implementation and must be replaced with evidence for the revised contract during implementation. No source or wiki file is changed by this planning revision.

## Confirmed facts and evidence

- `pi-extension/subagents/subagent-runtime-control.ts` owns child input hooks, `ask_question`, activity state, and auto-exit behavior.
- `pi-extension/subagents/index.ts` owns `.ask` delivery, running-child state, `subagent_message`, tmux steering, and bounded delivery acknowledgment.
- The protected runtime-control extension loads before profile extensions, so its matching `input` handler can short-circuit later transforms.
- Pi’s `AgentSession.prompt()` dispatches extension commands first, then emits `input`, and only queues steer/follow-up input when the event was not handled.
- Pi’s agent loop awaits all tool promises before another provider call. A pending `ask_question` therefore prevents interim model generation even when the assistant emitted sibling tool calls in the same batch.
- Current model-free tests already expose the child extension and parent steer seams; the lifecycle integration test already has an `ask_question` fixture but currently proves notification only.

## Impact

Assurance: medium - the change is local and reversible but crosses child tool execution, parent watcher state, terminal delivery, cancellation cleanup, and same-run model continuation. No dependency, persistent-data migration, production action, or public profile-schema change is required.

## Revised acceptance

- No provider request occurs after `ask_question` until the matching answer is consumed.
- The parent receives exactly one visible question notification containing the same question text.
- `subagent_message` routes an answer to the pending question through the existing safe tmux submission path and never exposes answer text in shell commands or argv.
- Slash-prefixed and multiline answers are delivered as data, not commands or separate turns.
- The child consumes only a valid envelope for its current question ID, returns the decoded answer as the tool result, and continues the same agent run without a duplicate user/steer message.
- One matching acknowledgment can confirm only one submitted answer. Timeout remains unconfirmed and never causes automatic resend or termination.
- Duplicate, malformed, stale, mismatched, aborted, and interrupted states do not resolve the wrong question or leak private envelopes into model context.
- Ordinary running messages and finished-session resume preserve current behavior.
